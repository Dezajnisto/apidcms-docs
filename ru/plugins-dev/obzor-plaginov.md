# 🔌 Плагины

Плагины расширяют функциональность apidcms без правки ядра. Каждый плагин — изолированная папка в `plugins/имя_плагина/`.

В ядро входят два плагина: **Account** (личный кабинет) и **Cart** (корзина).

---

## Где найти

В админ-панели: боковое меню → **Плагины** (иконка 🧩).

---

## Управление плагинами

### Список плагинов (`/admin/plugins`)

Таблица всех плагинов: название, версия, описание, статус. Доступны кнопки **Активировать** / **Деактивировать** и **Настроить**.

### Страница плагина (`/admin/plugins/имя`)

Три вкладки:

- **Инфо** — название, версия, статус, зависимости, содержимое `plugin.json`
- **Шаблоны** — список `.twig`-файлов плагина, кнопка «Редактировать»
- **Настройки** — форма с параметрами плагина (валюта, лимиты и т.д.)

### Редактор шаблонов (`/admin/plugins/имя/шаблонов/файл.twig`)

Полноценный редактор кода. Сохранение по Ctrl+S или кнопкой.

---

## Установка и удаление

- **Установка:** скопировать папку плагина в `plugins/имя_плагина/` на хостинге, затем активировать через админку
- **Удаление:** деактивировать в админке, затем удалить папку `plugins/имя_плагина/`
- **Вкл/выкл:** через админку кнопками Активировать/Деактивировать

> ⚠️ При удалении папки плагина таблицы в базе данных **остаются**. При деактивации — тоже.

### Где хранится «включён/выключен»

`"enabled"` в `plugin.json` — это значение **по умолчанию**, то, что шипится
вместе с плагином. Текущее состояние сайта хранится в
`storage/database/plugins-state.json` и перекрывает файл:

```json
{ "webchat": true, "cart": false }
```

Поэтому галочка в админке не меняет ни одного файла в git — раньше она
переписывала `plugin.json`, серверная копия расходилась с коммитом, и деплой
отказывал на проверке «файлы, которые правит CMS» до `--force`.

Хранить состояние в базе нельзя: `bootstrap.php` загружает плагины до
подключения к БД, и выключенный плагин успевал выполнить `init.php` по
значению из файла. `storage/database/` не уезжает деплоем и попадает в бэкапы
вместе с базой.

Удалить файл состояния — значит вернуть все плагины к значениям по умолчанию
из их манифестов.

## 🔐 Плагин Account — Личный кабинет

Регистрация, авторизация и профиль пользователей.

**Маршруты:**
- `/register` — регистрация
- `/login` — вход
- `/profile` — профиль
- `/logout` — выход

**Особенности:**
- Remember-me (cookie на 30 дней)
- Twig-функции: `is_logged_in()`, `current_user()`

**Таблицы:** `users`, `user_tokens`

---

## 🛒 Плагин Cart — Корзина

Добавление товаров в корзину для сайтов-каталогов.

**AJAX-эндпоинты:**
- `POST /cart/add` — добавить товар
- `POST /cart/update` — изменить количество
- `POST /cart/remove` — удалить товар

**Страницы:**
- `/cart` — корзина с +/- и удалением

**Twig-функции:** `cart_count()`, `cart_total()`

**Таблица:** `cart_items`

## 💬 Плагин WebChat — чат с ответами из MAX или Telegram

Чат-виджет для сайта: посетитель пишет в окно на странице, владелец отвечает
из мессенджера. Панель оператора держать открытой не нужно, история диалога
остаётся в базе сайта.

**Возможности:**
- Кнопка чата на всех страницах; окно, история, мобильная вёрстка
- Канал ответов — MAX или Telegram (выбирается в настройках), можно сменить позже
- В админке — список обращений, непрочитанные, поиск, ответ из панели
- Кнопка «Проверить подключение»: подписывает вебхук и отправляет тестовое сообщение
- Антиспам: лимиты на обращения и сообщения, IP хранится только как хеш

**Маршруты:**

| Путь | Назначение |
|---|---|
| `GET /chat/widget` | скрипт виджета (CSS встроен в ответ) |
| `POST /chat/api/start` | создать обращение, получить токен посетителя |
| `POST /chat/api/send` | сообщение посетителя |
| `GET /chat/api/poll` | новые сообщения |
| `POST /chat/api/hook/max` | вебхук MAX |
| `POST /chat/api/hook/telegram` | вебхук Telegram |
| `/admin/chats` | обращения и ответы |

> Скрипт виджета отдаётся адресом **без** расширения `.js`. Это сделано
> специально: обычное правило nginx `location ~* \.(css|js)$` отдаёт такие
> адреса статикой, и запрос не доходит до PHP.

**Таблицы:** `plugin_webchat_threads`, `plugin_webchat_messages`

## 🗣️ Плагин Community — форум, комментарии, сообщества

Один плагин на три задачи: обычный форум, комментарии к страницам сайта и
закрытые сообщества. Устроено так: **тема форума — обычная запись, у которой
есть поле `embed_code`**. Пусто — это тема форума; заполнено — тема привязана
к странице сайта и работает как комментарии к ней. Поэтому модерация, ответы,
цитаты, подписка на ответы и пагинация — общий код, а не три разных.

**Возможности:**
- Форум: разделы, темы, закрепление, закрытие темы, пагинация, просмотры
- Комментарии под текстом страницы или записи блога — без правки шаблонов темы
- Картинки в сообщениях (загрузка через форму, тип проверяется по содержимому)
- Markdown с безопасным режимом: сырой HTML экранируется, `javascript:` и `data:` вырезаются
- Очередь модерации в админке: «опубликовать / спам / удалить», счётчик в меню
- Антиспам: ловушка для ботов, минимальное время заполнения, лимиты по хешу адреса, стоп-слова
- Письма подписчикам темы через почтовые настройки сайта
- Работает и без плагина Account: тогда остаются гостевые комментарии с проверкой

**Каналы по режимам:**

| `mode` | Что | Кто создаёт темы | Где видно |
|---|---|---|---|
| `forum` | раздел форума | пользователи | `/forum/<slug>` |
| `comments` | служебный, скрытый | автоматически при первом комментарии | под текстом страницы |
| `community` | сообщество | участники | `/community/<slug>` |

**Маршруты:**

| Путь | Назначение |
|---|---|
| `GET /forum` | список разделов |
| `GET /forum/<раздел>` | темы раздела |
| `GET /forum/<раздел>/<тема>` | сообщения и форма ответа |
| `GET/POST /forum/<раздел>/new` | новая тема |
| `GET /community` | список сообществ |
| `GET /community/<slug>` | страница сообщества: обсуждения, участники |
| `POST /community/<slug>/join` | вступить или подать заявку |
| `POST /community/<slug>/leave` | выйти |
| `POST /community/<slug>/members` | действия модератора: одобрить, отклонить, назначить, убрать |
| `POST /forum/<раздел>/<тема>/reply` | ответ |
| `POST /community/reply` | комментарий к странице или записи |
| `POST /community/upload` | загрузка картинки (JSON) |
| `/admin/community` | очередь модерации |

**Сообщества.** Сообщество — тот же канал, только `mode = community`.
Политика вступления (`join_policy`): `open` — кнопкой сразу, `approval` —
заявкой с одобрением модератора, `closed` — только по приглашению.
Задаётся списком в `/admin/community`, не текстом в таблице.

Не-участник видит название, описание, число участников и кнопку вступления;
темы и список участников скрыты. Модератор канала одобряет заявки и убирает
участников сам, без админа сайта; себя понизить нельзя. О новой заявке
модераторам приходит письмо.

> Сообщества требуют плагин `account`: вступать некому на сайте без
> регистрации. Комментарии и гостевой форум работают и без него.

**Таблицы:** `plugin_community_channels`, `plugin_community_topics`,
`plugin_community_posts`, `plugin_community_followers`, `plugin_community_members`

**Свои стили:** `assets/community.css` не задаёт фон и наследует цвет текста
от темы, акцент берётся из `--accent-purple`, если тема его объявляет.

**К чему привязывается тема:**

| `embed_code` | Что это |
|---|---|
| `page:12` | страница сайта |
| `item:posts:7` | запись блога |
| `item:catalog:2` | запись любого раздела — каталог, товары |

Имя таблицы берётся из `nav_item->source_table`, поэтому записи разных
разделов с одинаковыми id не слипаются в одну тему.

**Если шаблон не печатает текст записи** (карточка каталога грузит текст
отдельным запросом), дописывать в контент некуда — тогда блок ставится перед
`</main>` на хуке `front.output`. Маркер `<!--apc-comments-->` не даёт вставить
его дважды. Настройка `comments_position`: `auto` (в тексте, а если его нет —
в конце страницы), `content` (только в тексте), `end` (всегда в конце).

Если нужно вставить блок в своё место в шаблоне — есть функция:

```twig
{{ community_comments(page) }}
```

**Антиспам.** IP не хранится: только `HMAC-SHA256(ip, секрет плагина)`.
По хешу считается частота, восстановить адрес нельзя. «Подозрительное»
не выбрасывается, а уходит в очередь проверки; стоп-слово и ловушка для
ботов — отказ.

---

> **Если плагин рисует свои страницы**, он рендерит их мимо
> `FrontController::render()` — и тогда фильтр `front.output` сам не сработает.
> Всё, что подписано на этот фильтр (стили плагина, виджеты, счётчики),
> на такой странице не появится. Прогоняйте готовый HTML через фильтр сами:
>
> ```php
> $html = \Core\PluginManager::getInstance()->applyFilters('front.output', $html, $fc);
> echo $html;
> ```
>
> Грабли реальные: форум отдавался без CSS, пока это не было добавлено.

## 🧩 Точки расширения (хуки)

Плагин подписывается на хуки через `PluginManager`. Экшены (`addAction`)
ничего не возвращают, фильтры (`addFilter`) получают значение и возвращают
изменённое.

| Хук | Тип | Когда | Зачем |
|---|---|---|---|
| `core.init` | экшен | загрузка ядра | ранняя инициализация плагина |
| `db.migrate` | экшен | загрузка с базой | создание и проверка таблиц |
| `twig.init` | экшен | инициализация фронтенд-Twig | свои шаблоны и функции на сайте |
| `front.router.before` | экшен | до маршрутизации | свои публичные маршруты (`$path`) |
| `front.router.after` | экшен | после маршрутизации | не срабатывает, если страница отдана |
| `front.render` | фильтр | перед рендером | добавить данные в шаблон |
| `front.output` | фильтр | готовый HTML | вставка виджета/счётчика на все страницы |
| `admin.routes` | экшен | сборка маршрутов админки | своя страница в админке |
| `admin.twig.init` | экшен | инициализация админ-Twig | путь к своим шаблонам |
| `admin.menu` | фильтр | вывод меню | пункт в боковом меню (с `order` и `badge`) |
| `admin.current_section` | фильтр | подсветка меню | какой пункт считать активным |

**Своя страница в админке.** Контроллер плагина живёт в своём namespace,
ядро находит его по имени класса с обратным слешем:

```php
$pm->addAction('admin.routes', function ($app) {
    $app->addRoute('/chats', 'Plugins\Webchat\AdminChatsController', 'index');
    $app->addRoute('/chats/{id}', 'Plugins\Webchat\AdminChatsController', 'thread');
}, 10, 'webchat');

$pm->addAction('admin.twig.init', function ($controller, $twig) use ($pluginDir) {
    $twig->getLoader()->addPath($pluginDir . '/views', 'webchat');
}, 10, 'webchat');
```

Контроллер наследуется от `Admin\BaseController`, шаблоны вызываются с
namespace: `$this->render('@webchat/chats.html.twig', [...])`.

> ⚠️ **Свой ответ из `front.router.before` всегда завершайте `exit`.** Если
> вернуть управление в `FrontController`, он нарисует свою 404 и перетрёт
> статус — ответ `304 Not Modified` или `204` превратится в `404` с пустым
> телом. На этом уже ловили «виджет пропадает через раз».

**Пункт меню** — массив с ключами `title`, `url`, `section` (совпадает со
значением, которое вернул фильтр `admin.current_section`), `badge` (число для
красного счётчика) и `order` (сортировка, по умолчанию 50):

```php
$pm->addFilter('admin.menu', function ($items) {
    $items[] = ['title' => 'Чаты', 'url' => '/admin/chats', 'section' => 'chats', 'badge' => 3, 'order' => 60];
    return $items;
}, 10, 'webchat');
```

**Виджет на всех страницах** вставляется фильтром `front.output` — единственным
способом, который не требует правки шаблонов каждой темы:

```php
$pm->addFilter('front.output', function ($html) {
    return str_replace('</body>', '<script src="/chat/widget" defer></script></body>', $html);
}, 10, 'webchat');
```

## Настройки плагинов

Каждый плагин может объявить настраиваемые параметры в `plugin.json` — валюта,
лимиты, поведение. Фактические значения хранятся в базе сайта, в таблице
`plugin_settings`, а не в манифесте: манифест — это код, он лежит в git и уезжает
деплоем, а настройки принадлежат конкретному сайту, и часть из них секретна.
Таблица создаётся автоматически при первом обращении, миграция не нужна.

```json
"settings": [
  {
    "key": "currency",
    "type": "text",
    "value": "₽",
    "label": "Валюта",
    "description": "Символ валюты для отображения цен"
  },
  {
    "key": "payment_secret",
    "type": "text",
    "secret": true,
    "value": "",
    "label": "Секретный ключ платёжного шлюза"
  }
]
```

`value` здесь — значение по умолчанию, то есть то, что видно в git. Редактор
настроек в админке (вкладка «Настройки» на странице плагина) пишет введённое в
`plugin_settings`. Плагин читает значение как обычно:

```php
$pm = \Core\PluginManager::getInstance();
$cfg = $pm->getPlugin('cart');
foreach ($cfg['settings'] as $s) {
    if ($s['key'] === 'currency') { $currency = $s['value']; }
}
```

Откуда взялось значение, плагин не знает и знать не должен.

Типы поля в форме настроек: `text` (по умолчанию), `textarea`, `number`,
`checkbox`, `select` (со словарём `options`) и `secret` — флаг, который
действует поверх любого типа.

### Флаг `secret`

`"secret": true` помечает ключи и пароли. Такое значение не выводится в HTML
(поле-пароль, пустая отправка означает «не менять», очистка — отдельной
галочкой), маскируется как `***` на вкладке «Инфо» и никогда не записывается
обратно в `plugin.json` — ни при сохранении настроек, ни при включении или
выключении плагина.

Если в манифесте ещё осталось значение с этим флагом (у старой версии плагина),
ядро при первом же запросе переносит его в базу, обнуляет в файле и пишет
строку в `error_log`. Так обновление не теряет ключ и не оставляет его в коде.

## 📊 Таблицы плагинов в админке

Плагины могут объявлять свои таблицы через поле `tables` в `plugin.json`. Это позволяет админке показывать таблицы плагина на главной странице в отдельной группе «Плагины» (рядом с системными и пользовательскими).

**Пример plugin.json с таблицами:**

```json
{
  "name": "account",
  "version": "1.0.0",
  "description": "Личный кабинет",
  "tables": ["plugin_account_users", "plugin_account_tokens"]
}
```

После добавления поля `tables` таблицы плагина появятся в секции «Плагины» на дашборде админки.

## 🏷️ Соглашение об именовании таблиц

Все таблицы плагинов должны использовать префикс `plugin_{name}_`. Это предотвращает конфликты имён с пользовательскими таблицами (например, если пользователь создаст таблицу `users` через админку, а плагин Account попытается создать свою).

**Формат:** `plugin_{имя_плагина}_{назначение}`

**Примеры:**
- `plugin_account_users` — таблица пользователей плагина Account
- `plugin_cart_items` — таблица элементов корзины плагина Cart
- `plugin_credits_transactions` — таблица транзакций плагина Credits

**Правила:**
- Имя плагина — только `[a-z][a-z0-9]*` (без подчёркиваний)
- Имя таблицы — строчные буквы и подчёркивания
- Полное имя: `plugin_{name}_{purpose}`

### Миграции с верификацией схемы

Каждая миграция плагина должна не только создавать таблицы (`CREATE TABLE IF NOT EXISTS`), но и верифицировать схему существующих таблиц через `PRAGMA table_info` и `ALTER TABLE ADD COLUMN`. Это гарантирует, что при обновлении плагина новые колонки будут добавлены без потери данных.

**Пример миграции с PRAGMA-верификацией:**

```php
$pm->addAction('db.migrate', function ($db) use ($pluginDir) {
    $migrationFile = $pluginDir . '/migrations/001_create.sql';
    if (!file_exists($migrationFile)) return;
    $sql = file_get_contents($migrationFile);
    $statements = array_filter(array_map('trim', explode(';', $sql)));
    foreach ($statements as $stmt) {
        if (!empty($stmt)) {
            try { $db->exec($stmt); }
            catch (\Exception $e) { error_log("Migration error: " . $e->getMessage()); }
        }
    }

    // Schema verification
    $expectedColumns = [
        'plugin_myplugin_items' => [
            'id' => 'INTEGER',
            'name' => 'TEXT',
            'created_at' => 'DATETIME'
        ]
    ];

    foreach ($expectedColumns as $table => $columns) {
        try {
            $existing = $db->query("PRAGMA table_info(\"{$table}\")")->fetchAll();
            $existingNames = array_column($existing, 'name');
            foreach ($columns as $colName => $colType) {
                if (!in_array($colName, $existingNames)) {
                    $db->exec("ALTER TABLE \"{$table}\" ADD COLUMN \"{$colName}\" {$colType} DEFAULT ''");
                    error_log("Added missing column {$table}.{$colName}");
                }
            }
        } catch (\Exception $e) {
            error_log("Schema verification error: " . $e->getMessage());
        }
    }
}, 10, 'myplugin');
```

### Внешние ключи

Если таблица ссылается на таблицу другого плагина (например, `plugin_account_users`), плагин должен:
- Указать зависимость в `plugin.json`: `"dependencies": ["account"]`
- Использовать полное имя таблицы в FOREIGN KEY
