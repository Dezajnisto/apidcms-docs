# 🔌 MCP-сервер

MCP (Model Context Protocol) — стандарт, по которому AI-клиент (Cursor, [CC],
любой агент с поддержкой MCP) узнаёт, что умеет сервер, и вызывает его
инструменты.

apidcms отдаёт MCP по адресу `/mcp`. Это **не второй API**: инструменты вызывают
те же сервисы ядра, что и `/api/v1` (схема, проверка записи, журнал), поэтому
MCP и HTTP не могут разойтись. Встроенный ассистент в админке ходит в тот же
каталог инструментов.

---

## Подключение

Нужен токен API: тот же, что для `/api/v1` (запросы без него отклоняются).

Если ваш клиент умеет MCP по HTTP:

```json
{
  "mcpServers": {
    "mysite": {
      "type": "http",
      "url": "https://example.com/mcp",
      "headers": {
        "Authorization": "Bearer <token>"
      }
    }
  }
}
```

Транспорт — Streamable HTTP, JSON-RPC 2.0, без сессий: один запрос — один ответ,
ничего не хранится между вызовами. Проверить руками:

```bash
curl -X POST https://example.com/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## Инструменты

| Инструмент | Что делает |
|---|---|
| `schema.get` | весь проект одним вызовом: таблицы, колонки (тип, обязательность, допустимые значения, подпись, формат), внешние ключи, связи many-to-many, карта страниц |
| `records.list` | записи таблицы: `limit`, `offset`, `sort`, `order`, `search` |
| `records.get` | одна запись по `id` |
| `records.create` | создать запись (проверка полей, как в API) |
| `records.update` | обновить запись (возвращает изменённые колонки) |
| `records.delete` | удалить запись |
| `navigation.get` | карта страниц: какая таблица питает какой URL каким шаблоном |
| `relations.list` | связи many-to-many, при желании для одной таблицы |
| `audit.list` | журнал записей: метод, таблица, строка, диф |
| `docs.list` | оглавление документации (дёшево) |
| `docs.get` | одна статья документации по slug |
| `docs.search` | поиск статьи по словам из вопроса |

Все изменяющие инструменты принимают `dry_run: true` — посмотреть, что
изменится и какие страницы это затронет, ничего не записав.

Отказ в записи приходит как `isError: true` и список полей:

```json
{
  "error": "validation_failed",
  "table": "catalog",
  "action": "insert",
  "fields": [
    {"column": "price", "rule": "type", "got": "1500 руб", "expected": "integer (INTEGER)"}
  ]
}
```

Модель видит это и исправляется сама — именно поэтому проверка записи делалась
до MCP, а не после.

## Ресурсы

Кроме инструментов MCP отдаёт **ресурсы** — данные, которые клиент может
прочитать по ссылке, не вызывая инструмент:

| URI | Что внутри |
|---|---|
| `apidcms://schema` | схема проекта (JSON) |
| `apidcms://navigation` | карта страниц (JSON) |
| `apidcms://docs/toc` | оглавление документации (JSON) |
| `apidcms://docs/{slug}` | статья документации (Markdown) |

Документация как ресурс — не украшение: клиент может держать под рукой
оглавление и подтягивать одну статью, когда она нужна, вместо того чтобы
загружать весь справочник в контекст.

---

## Что это даёт на практике

Агент с токеном, зная только адрес сайта, за два вызова получает полную картину:
`schema.get` → что за таблицы, что в них значит каждая колонка, какие есть
страницы и какая таблица питает какой URL. Дальше — `records.*` чтобы читать и
писать, `docs.*` чтобы отвечать про саму CMS.

Это же закрывает разрыв «записал, а на сайте не видно»: `dry_run` и ответ
инструмента показывают `affected_urls` — страницы, которые собираются из
этой таблицы.

---

## Безопасность

- доступ только по Bearer-токену, тот же, что у `/api/v1`;
- внутренние таблицы (`system_*`, `users`, `user_tokens`, `entity_relations`,
  `visit_stats`, `table_meta`, `field_meta`, `api_idempotency`) инструментам
  недоступны;
- каждая запись через MCP попадает в журнал с пометкой `actor: mcp`;
- токен один и даёт доступ ко всем данным проекта — скоупов (`read` / `content` /
  `full`) пока нет, поэтому токен для агента стоит держать отдельно и менять
  после экспериментов.
