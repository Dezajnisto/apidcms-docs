# v2.7.1 — nginx-пример не отдаёт 403 на страницы каталога плагинов

**Дата:** 16 ноября 2026
**Тип:** patch

## Что было

В примере конфига для nginx (`docs/nginx.conf.example`) стоит правило:

```nginx
location ~ ^/(core|config|storage|themes|plugins|tmp)/ {
    deny all;
}
```

Оно закрывает исходники — и заодно живые страницы. Тип страницы `external`
(каталог из внешнего JSON) обслуживает элементы по адресу `/<url>/<слаг>`: для
каталога плагинов это `/plugins/yookassa`. Правило совпадает по **префиксу URL**,
поэтому страница получала 403 при полностью рабочем остальном сайте.

Файлов там быть не может: корень сайта — `www/`, а `plugins/` и `themes/` лежат
на уровень выше, вне веб-корня. То есть запрет в этой части был политикой, а не
защитой, и политика ломала страницу.

## Что исправлено

Перед запретом добавлено исключение:

```nginx
# /plugins и /plugins/<слаг> — маршрут CMS (navigation → external), а не файлы.
# Регексп-локейшны проверяются в порядке появления, поэтому исключение выше.
location ~ ^/plugins/[A-Za-z0-9_-]+/?$ {
    rewrite ^ /index.php?$query_string last;
}
```

Точки в наборе символов нет, поэтому `/plugins/<имя>/plugin.json` по-прежнему
попадает под запрет — как и любой другой путь с расширением.

В `docs/external-page-type.md` раздел про каталог плагинов теперь предупреждает
об этой грабле и показывает готовый блок для конфига.

## Как проверить у себя

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://ваш-сайт/plugins        # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ваш-сайт/plugins/имя    # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ваш-сайт/plugins/имя/plugin.json  # 403
```

Если у сайта нет страницы `/plugins`, менять ничего не нужно: правило касается
только тех, кто сделал каталог плагинов страницей CMS.
