# v2.3.0 — robots.txt and sitemap.xml from the CMS

**Date:** November 11, 2026
**Type:** feature

## New

**`raw` page type** — renders a theme template as-is, without the site layout,
with a configurable `Content-Type`. Until now `robots.txt` and `sitemap.xml`
could not be served from the admin panel: `page` requires a record in `pages`,
`landing` renders through `base.html.twig` (a full HTML document), and any other
type falls through to the dynamic list and returns 404.

A `navigation` record for robots.txt:

| Field | Value |
|------|-------|
| `url` | `robots.txt` |
| `page_type` | `raw` |
| `template` | `robots` → `themes/<theme>/front/robots.html.twig` |
| `location` | `none` — keeps the file out of the menu |
| `page_config` | `{"content_type": "text/plain; charset=utf-8"}` |

For `sitemap.xml` the same with `content_type` = `application/xml; charset=utf-8`
and the `sitemap.xml.html.twig` template. Building the sitemap content (collecting
links) stays in the template — the core only serves the file.

If the theme has no such template, `core/views/front/robots.html.twig` is used
(`User-agent: *` + `Disallow:`). If neither exists — 404.

Details: [Navigation and Menu](../en/content/navigaciya-i-menu.md).

## Fixed

**`FOREIGN KEY constraint failed` when saving a record in the admin panel.** The
form submits an empty string for every field left untouched, and `create()`
(unlike `update()`) did not turn it into `NULL`. SQLite stores `''` in an INTEGER
column as TEXT, so an empty foreign key (`navigation.page_id`,
`menu_items.page_id`, `docs.section_id`, `sections.page_id`, `gallery.section_id`)
failed the constraint check and the record was not saved at all.

The same defect silently corrupted numeric columns without a foreign key:
`menu_order` and `parent_id` were stored as the text `''` instead of `0`.

Empty values are now normalized in one place (`Database::normalizeEmptyValues()`):

- nullable non-text column → `NULL`;
- NOT NULL numeric column → `0` (an unchecked checkbox no longer writes text);
- text columns are untouched — `''` is a meaningful value there.

The normalization also applies to inline cell editing.
