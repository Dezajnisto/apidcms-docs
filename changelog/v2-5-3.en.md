# v2.5.3 — plugins load by dependency, and their `/api/*` routes work again

**Date:** November 16, 2026
**Type:** fix

## Why

Every request on enfesto.ru left a log line: "plugin enfesto-license not loaded —
dependencies not satisfied". It looked like noise. It turned out to be two bugs,
each breaking real functionality.

## What was wrong

**1. Plugins loaded in alphabetical order.** `PluginManager::loadPlugins()`
iterated directories in the order `glob()` returns them and checked dependencies
against plugins already loaded. So a plugin whose dependency sorts later
alphabetically never loaded **at all**: `enfesto-license` depends on
`subscription`, and "e" comes before "s". It only half-worked because
`loadPlugins()` runs twice per request — on the second pass the configs are
already registered. In other words the plugin worked halfway and in the wrong
order.

**2. The core claimed every `/api/*` path.** `router.php` tested
`strpos($uri, 'api') === 0`, so any plugin route under `/api/` received the core's
answer "the path must start with /api/v1/". That killed:

- `enfesto-license`: `/api/license/register|login|status|license` and
  `/api/catalog` — the REST API the Enfesto desktop app runs on;
- `favorites` on bajto.ru: `/api/favorites/toggle` and `/api/favorites/list`;
- `prompts-feed` on bajto.ru: `/api/feed/create` and `/api/feed/delete`.

The plugins registered those routes through `front.router.before` — a hook the
request never reached.

## What changed

- loading in three steps: read all `plugin.json` → compute the order with a depth
  first walk (dependencies first, cycles detected) → load `init.php` in that
  order;
- the core answers only for `/api/v1`; other `/api/*` paths reach the plugins;
- the log line now names the real cause: "needs plugin X, but it is disabled",
  "it is missing from plugins/", "circular dependency";
- `activate()` refuses to enable a plugin whose dependencies are disabled or not
  loaded and shows the reason in the admin panel; `deactivate()` refuses to
  disable a plugin that enabled plugins depend on;
- `plugin.json` no longer receives an absolute path to the plugin directory — it
  leaked into the project's git (bajto.ru still had a path from the old host).

## How to check

```
GET https://enfesto.ru/api/catalog
→ 200 {"ok":true,"items":[…]}
```

Before: `404 {"error":{"code":"not_found","message":"Путь должен начинаться с /api/v1/"}}`.

```
GET https://bajto.ru/api/favorites/list
→ 401 {"error":"Not logged in"}      # no session — as expected
```

## Compatibility

One behaviour change: an unknown path like `/api/<anything>` now returns the
site's regular 404 page instead of the core's JSON error. That prefix belongs to
plugins, not to the core; `/api/v1` works exactly as before.
