# v2.6.0 — агент может всем управлять: токены со скоупами, связи через API, документация без сети

**Дата:** 16 ноября 2026
**Тип:** minor

## Зачем

Три вещи упирались друг в друга. Токен API был один, безымянный и «на всё» —
подключать к нему агента было страшно, а без него нельзя. Связи many-to-many
читались через `/relations`, но записать их было нечем: `entity_relations`
скрыта из `/tables`, и внешний агент не мог положить товар в категорию. А
документация тянулась с GitHub на каждый запрос — на сервере, где GitHub не
отвечает, это 10 секунд ожидания в каждом обращении к справке.

## Токены со скоупами и экран «Настройки → API»

Токен стал ключом **с правами**:

| Скоуп | Что разрешено |
|---|---|
| `read` | только `GET`: схема, навигация, связи, таблицы, документация |
| `content` | `read` плюс запись в пользовательские таблицы и статьи |
| `full` | всё, включая шаблоны и служебные ручки |

В админке появился экран: список токенов, создание с именем и скоупом, показ
токена **один раз**, отзыв, дата последнего использования. В базе лежит только
`sha256(token)` — сам токен восстановить нельзя. Таблица `api_tokens`
создаётся лениво, как `table_meta`, миграция не нужна.

Права проверяются в `Api\Auth`, а не в каждом контроллере: `read` на запись
получает `403 insufficient_scope`, а фактический скоуп виден в заголовке
`X-apidcms-scope`. `/mcp` — всегда POST, поэтому для него проверка идёт по
инструменту: `read`-токен может читать и не может вызвать `records.create`,
`relations.add` и прочие изменяющие инструменты. Журнал `/api/v1/audit`
(`audit.list` в MCP) доступен только с `content`: там IP клиентов и дифы
чужих записей.

Старый `system_settings.api_key` продолжает работать со скоупом `full`:
обновление не выключает существующие интеграции. Но отозвать его из админки
нельзя — экран честно предупреждает об этом.

Имя таблицы — `api_tokens`, а не `user_tokens`: на части сайтов `user_tokens`
уже занята «запомнить меня» с другой схемой (`user_id`, `type`,
`expires_at`), и совпадение имён молча сломало бы вход.

## Запись связей many-to-many

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/v1/relations/{table}/{id}` | связи одной записи |
| `POST` | `/api/v1/relations` | связать: `{source_table, source_id, relation_name, target_ids[]}` |
| `DELETE` | `/api/v1/relations` | снять связи (пустой `target_ids` — снять все) |

Проверяется всё, что можно проверить до записи: таблица, запись, имя связи и
каждая цель. Дубль не создаётся — уже существующая связь возвращается в
`changes.already` (в `entity_relations` нет уникального индекса, простой
`INSERT` удвоил бы строки). Работают `?dry_run=1`, `Idempotency-Key` и журнал.

Целевая таблица связи берётся из `navigation.page_config.relations` — оттуда же,
откуда её берёт форма в админке, а не угадывается по имени. Если проект связь не
объявлял, работает прежнее правило «имя связи = имя таблицы».

Те же действия доступны агенту как MCP-инструменты `relations.add` и
`relations.remove`, поэтому ассистент и внешний агент делают одно и то же.

## Документация через API

| Метод | Путь | Что отдаёт |
|---|---|---|
| `GET` | `/api/v1/docs` | оглавление статей |
| `GET` | `/api/v1/docs?q=слова` | поиск по заголовкам, описаниям и текстам |
| `GET` | `/api/v1/docs/{slug}?lang=ru\|en` | статья в Markdown |
| `POST` | `/api/v1/docs/refresh` | обновить кэш из GitHub |

`DocsFetcher` перестал быть «кэш с TTL, который всё равно ходит в сеть»: кэш —
источник правды, сеть нужна только для явного обновления (`refreshManifest`,
`refreshDoc`, `refreshAll`). Сбой обновления не стирает рабочую копию, а
`GET /api/v1/docs` показывает `status.stale` — насколько кэш старый.

Заодно `DocIndex` учитывает язык: `?lang=en` больше не отдаёт русский заголовок
статьи при английском тексте.

## Мелочи

- `system_audit.token_id` наконец заполняется: в журнале видно, какой токен
  сделал запись, а не только `actor: api`.
- Ответы `/api/v1` называют токены, связи и документацию в `notes`, а
  `capabilities` помечает `tokens.scopes` и `docs` как готовые.
- Проверка записи через API не менялась: правила по-прежнему из
  `table_meta`/`field_meta` и `PRAGMA`, отказ — `422` со списком полей.
