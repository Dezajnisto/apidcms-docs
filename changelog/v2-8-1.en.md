# v2.8.1 — the plugin on/off state no longer writes to plugin.json

**Date:** 27 November 2026
**Type:** patch

## What was wrong

The "Activate / Deactivate" button on a plugin page rewrote
`plugins/<name>/plugin.json` — a file tracked by git. Every toggle made the server
copy drift from the commit.

On its own that looks harmless, but it has a price: any deploy that checks "was
this file edited in the browser" (comparing the server against the last commit)
starts refusing. You end up passing `--force`, which overwrites server-side edits
blindly. Rolling one plugin out to eight sites hit this eight times in a row, and
each time someone had to verify by hand that no foreign edit sat on the server.

## What is fixed

The on/off state now lives in `storage/database/plugins-state.json`:

```json
{ "webchat": true, "cart": false }
```

`"enabled"` in `plugin.json` remains the **default** — the value that ships with
the plugin. The state file overrides it, so:

- the admin toggle changes no file tracked by git — deploys stop refusing;
- a site where a plugin was turned off keeps it off even after a deploy brings
  `"enabled": true` back from the repository;
- deleting the state file returns every plugin to the default from its manifest.

Writes go through a temporary file and `rename`: a crash mid-write cannot leave
half a JSON file, which would mean "all plugins at their defaults".

## Why not the database

The first instinct was to put the state into `plugin_settings`, next to the other
plugin settings. It does not work: `bootstrap.php` loads plugins **before** the
database connection exists. A disabled plugin still ran its `init.php` from the
value in the file — that is, turning it off in the admin panel simply did not
work. Verified on the stand: the state from the database is only read on the
second `loadPlugins()` call, by which time `init.php` has already run.

`storage/database/` is not deployed and is backed up together with the database,
so the site state lives where the site's data lives.

## How to update

```bash
git pull
```

and redeploy the core to your site. No migration is needed: while the state file
does not exist, the values from the manifests apply — exactly as before.
