# v2.6.0 — an agent can run everything: scoped tokens, relation writes, docs without the network

**Date:** 16 November 2026
**Type:** minor

## Why

Three things blocked each other. The API had exactly one token: unnamed, all
powerful, impossible to revoke — giving it to an agent was scary, and without it
there was nothing to give. Many-to-many links could be read through `/relations`
but not written: `entity_relations` is hidden from `/tables`, so an external
agent could not put a product into a category. And the documentation was fetched
from GitHub on every request — on a server where GitHub is unreachable that was
a 10-second wait every time the help was needed.

## Scoped tokens and the "Settings → API" screen

A token is now a key **with rights**:

| Scope | What it allows |
|---|---|
| `read` | `GET` only: schema, navigation, relations, tables, documentation |
| `content` | `read` plus writes to user tables and articles |
| `full` | everything, templates and service endpoints included |

The admin has a screen: list, create with a name and a scope, show the token
**once**, revoke, last-used date. Only `sha256(token)` is stored — the token
itself cannot be recovered. The `api_tokens` table is created lazily, like
`table_meta`, so no migration is needed.

Rights are checked in `Api\Auth`, not in every controller: a `read` token that
writes gets `403 insufficient_scope`, and the applied scope is visible in the
`X-apidcms-scope` header. `/mcp` is always POST, so there the check is per tool:
a `read` token can read and cannot call `records.create`, `relations.add` and
other mutating tools. The `/api/v1/audit` log (`audit.list` in MCP) needs
`content`: it holds client IPs and write diffs.

The legacy `system_settings.api_key` keeps working with the `full` scope, so
upgrading does not switch existing integrations off. It cannot be revoked from
the admin — the screen says so plainly.

The table is named `api_tokens`, not `user_tokens`: on some sites `user_tokens`
already holds "remember me" data with a different schema (`user_id`, `type`,
`expires_at`), and a name collision would silently break logins.

## Writing many-to-many links

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/relations/{table}/{id}` | links of one record |
| `POST` | `/api/v1/relations` | link: `{source_table, source_id, relation_name, target_ids[]}` |
| `DELETE` | `/api/v1/relations` | unlink (empty `target_ids` unlinks all) |

Everything that can be checked is checked before writing: the table, the record,
the relation name and every target. An existing link is not duplicated — it is
reported in `changes.already` (`entity_relations` has no unique index, so a plain
`INSERT` would double rows). `?dry_run=1`, `Idempotency-Key` and the audit log all
work.

The target table of a relation comes from `navigation.page_config.relations` —
the same place the admin form reads it, instead of guessing by name. Projects
that never declared the relation keep the old "relation name equals table name"
fallback.

The same actions are available to agents as MCP tools `relations.add` and
`relations.remove`, so the built-in assistant and an external agent do the same
thing.

## Documentation over the API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/docs` | table of contents |
| `GET` | `/api/v1/docs?q=words` | search titles, descriptions and bodies |
| `GET` | `/api/v1/docs/{slug}?lang=ru\|en` | one article as Markdown |
| `POST` | `/api/v1/docs/refresh` | refresh the cache from GitHub |

`DocsFetcher` is no longer "a cache with a TTL that still hits the network": the
cache is the source of truth and the network is only used for an explicit refresh
(`refreshManifest`, `refreshDoc`, `refreshAll`). A refresh keeps itself inside a
time budget so an unreachable network cannot turn it into a fatal timeout, and
`GET /api/v1/docs` reports `status.stale` — how old the cache is.

`DocIndex` now honours the language too: `?lang=en` no longer returns a Russian
article title next to English text.

## Smaller things

- `system_audit.token_id` is finally filled in: the log shows which token made a
  write, not just `actor: api`.
- `/api/v1` responses mention tokens, relations and documentation in `notes`,
  and `capabilities` marks `tokens.scopes` and `docs` as ready.
- Write validation is unchanged: rules still come from `table_meta`/`field_meta`
  and `PRAGMA`, a refusal is still `422` with a field list.
