# v2.7.1 — the nginx example no longer answers 403 on plugin catalog pages

**Date:** 16 November 2026
**Type:** patch

## What was wrong

The nginx example config (`docs/nginx.conf.example`) shipped this rule:

```nginx
location ~ ^/(core|config|storage|themes|plugins|tmp)/ {
    deny all;
}
```

It closes off the sources — and live pages with them. The `external` page type
(a catalog built from an external JSON) serves its items at `/<url>/<slug>`: for
a plugin catalog that is `/plugins/yookassa`. The rule matches by **URL prefix**,
so the page answered 403 while the rest of the site worked fine.

No file can live there anyway: the site root is `www/`, while `plugins/` and
`themes/` sit one level above it, outside the document root. In that part the
deny was policy rather than protection, and the policy broke a page.

## What was fixed

An exception now comes before the deny:

```nginx
# /plugins and /plugins/<slug> are CMS routes (navigation → external),
# not files. Regex locations are checked in order, so this comes first.
location ~ ^/plugins/[A-Za-z0-9_-]+/?$ {
    rewrite ^ /index.php?$query_string last;
}
```

There is no dot in the character class, so `/plugins/<name>/plugin.json` still
falls under the deny rule — as does any other path with an extension.

The plugin catalog section of `docs/external-page-type.md` now warns about the
trap and shows the ready-made block.

## How to check your own site

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://your-site/plugins        # 200
curl -s -o /dev/null -w '%{http_code}\n' https://your-site/plugins/name   # 200
curl -s -o /dev/null -w '%{http_code}\n' https://your-site/plugins/name/plugin.json  # 403
```

If your site has no `/plugins` page, there is nothing to change: the rule only
affects those who made the plugin catalog a CMS page.
