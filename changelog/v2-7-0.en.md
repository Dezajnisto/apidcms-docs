# v2.7.0 — plugin settings live in the database, not in plugin.json

**Date:** 16 November 2026
**Type:** minor

## Why

A plugin manifest (`plugins/<name>/plugin.json`) is code: it is committed, it is
deployed and it ends up in code backups. Settings are not code — they are
per-site values, and some of them are secrets (a payment gateway key, a licence
signing key). While they lived in the manifest, a live payment key travelled
through the repository and through backups for years.

The only defence was a `.gitignore` line in the one project where the key had
appeared. That hid the whole file from git: a fresh clone and a staging stand
ended up with **no manifest at all**, and `PluginManager` silently skipped the
plugin folder — the plugin simply did not exist, with no way to tell why.

## What changed

**The manifest holds the schema, the database holds the values.**

```json
{
  "key": "yookassa_secret_key",
  "type": "text",
  "secret": true,
  "value": "",
  "label": "YooKassa Secret Key"
}
```

`value` is the default — the thing git is allowed to see. The actual value comes
from the `plugin_settings` table:

```sql
plugin TEXT, setting_key TEXT, setting_value TEXT, updated_at DATETIME
PRIMARY KEY (plugin, setting_key)
```

The table is created lazily, like `api_tokens` and `table_meta`: a core update
needs no manual migration. It is a separate table, not `system_settings`,
because `system_settings` is exposed in the API schema and read by the
assistant — no place for secrets.

**Plugin code does not change.** Plugins already read their settings through
`$pm->getPlugin('name')['settings'][i]['value']`; the core overlays the database
values before the plugin touches them, so a plugin never learns where they come
from.

The two states are explicit: no row — the default from the manifest is used;
a row that is empty — the owner cleared the value.

## The `secret` flag

A setting with `"secret": true` behaves differently:

| Where | Behaviour |
|---|---|
| Settings form | password field, the value is never rendered into HTML; an empty submit means "keep it"; clearing is a separate checkbox |
| "Info" tab (contents of `plugin.json`) | the value is masked as `***` |
| Manifest writes | the value never reaches the file, neither when settings are saved nor when the plugin is activated/deactivated |

## Moving existing secrets

If `plugin.json` still carries a `secret: true` value, the core does this on the
first request after the update:

1. copies the value into `plugin_settings`;
2. blanks it in the file (if the file is writable — on production `plugins/` is
   read-only for PHP, in which case the deploy brings the blanked file);
3. writes `plugin_settings: adopted <name>.<key>` into `error_log`.

The opposite case — a secret in the file while the database already has a value:
the file copy is ignored (the database wins), removed from the file and logged.
Without that, a hand-edited manifest would look like it worked while keeping a
live key in the code forever.

## How to migrate

1. Update the core. The site keeps working as before, values still come from the
   manifest for now.
2. Mark the key-like settings with `"secret": true` and leave `"value": ""`.
3. Deploy. On the first request the value moves into the database and the file
   is blanked.
4. Remove the `.gitignore` line that hid `plugin.json` and commit the manifest
   with the empty value.

The order matters: the core goes first (it knows how to adopt), and only then
the manifest with the empty value travels through git — otherwise the key is
simply lost.
