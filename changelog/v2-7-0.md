# v2.7.0 — настройки плагинов живут в базе, а не в plugin.json

**Дата:** 16 ноября 2026
**Тип:** minor

## Зачем

Манифест плагина (`plugins/<имя>/plugin.json`) — это код: он лежит в git,
уезжает деплоем и попадает в бэкапы кода. А настройки — не код: это значения
конкретного сайта, и часть из них секретна (ключ оплаты, ключ подписи лицензий).
Пока они жили в манифесте, живой ключ платёжного шлюза годами ездил через
репозиторий и бэкапы.

Способ борьбы был один — строка в `.gitignore` того проекта, где ключ завёлся.
Это прятало файл от git целиком: свежий клон и стенд оставались **без манифеста
вообще**, и `PluginManager` молча пропускал каталог плагина — плагина «нет», и
понять почему неоткуда.

## Что изменилось

**Манифест хранит схему, база — значения.**

```json
{
  "key": "yookassa_secret_key",
  "type": "text",
  "secret": true,
  "value": "",
  "label": "YooKassa Secret Key"
}
```

`value` — это значение по умолчанию, оно же то, что видно в git. Фактическое
значение подставляет таблица `plugin_settings`:

```sql
plugin TEXT, setting_key TEXT, setting_value TEXT, updated_at DATETIME
PRIMARY KEY (plugin, setting_key)
```

Таблица создаётся лениво, как `api_tokens` и `table_meta`: обновление ядра
не требует ручных миграций. Отдельная таблица, а не `system_settings`, потому
что `system_settings` выгружается в схему API и читается ассистентом — секретам
там не место.

**Код плагинов не меняется.** Все плагины и раньше читали настройки через
`$pm->getPlugin('имя')['settings'][i]['value']` — ядро подставляет значения из
базы до того, как плагин к ним обратится, поэтому плагин не знает, откуда они.

Два состояния различаются явно: строки в базе нет — берётся значение по
умолчанию из манифеста; строка есть и пустая — владелец её очистил.

## Флаг `secret`

Настройка с `"secret": true` ведёт себя иначе:

| Где | Поведение |
|---|---|
| Форма настроек | поле-пароль, значение не выводится в HTML; пустая отправка = «не менять»; очистка — отдельной галочкой |
| Вкладка «Инфо» (содержимое `plugin.json`) | значение маскируется как `***` |
| Запись манифеста | значение не попадает в файл ни при сохранении настроек, ни при включении/выключении плагина |

## Перенос старых секретов

Если в `plugin.json` ещё лежит значение с `secret: true`, ядро при первом же
запросе после обновления:

1. копирует значение в `plugin_settings`;
2. обнуляет его в файле (если файл доступен на запись — на проде `plugins/`
   доступен только на чтение, тогда файл придёт обнулённым с деплоем);
3. пишет в `error_log` строку `plugin_settings: plugin_settings adopted имя.ключ`.

Обратный случай — секрет лежит в файле, а в базе уже есть значение: файловая
копия игнорируется (база главнее), удаляется из файла и тоже попадает в лог.
Раньше такая «ручная правка» жила бы в файле вечно и выглядела бы рабочей.

## Как переехать

1. Обновить ядро. Сайт начнёт работать как раньше, значения пока берутся из
   манифеста.
2. Добавить `"secret": true` тем настройкам, которые являются ключами, и
   оставить `"value": ""`.
3. Задеплоить. При первом запросе значение уедет в базу, файл обнулится.
4. Убрать из `.gitignore` строку, которая прятала `plugin.json`, и закоммитить
   манифест с пустым значением.

Порядок важен: сначала обновляется ядро (оно умеет переносить), и только потом
в git уезжает манифест с пустым значением — иначе ключ просто потеряется.
